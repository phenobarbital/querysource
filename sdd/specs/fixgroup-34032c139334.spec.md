## 1. Motivation & Business Requirements

### Problem Statement
`rust/src/bigquery_parser.rs::bq_filter_conditions` renders two caller-controlled
strings into SQL without validation:

1. **The top-level filter key** (`process_entry`, line 142). Numeric keys are
   double-quoted; every other key is used verbatim as the column expression.
   The Cython twin validates it as a safe identifier (`bigquery.pyx:185`,
   FEAT-103) and the PostgreSQL Rust builder does too (`pg_safe_identifier_key`,
   `pgsql_parser.rs:25`). With FEAT-180 a key now also reaches the
   `LIKE` / `NOT LIKE` partial-matching forms (`bq_partial_match_condition`),
   which is what ledger issue `issue:aa699dd75abf` reports.
2. **The dict member key** used for JSON extraction (`process_dict_value`,
   line 221): `JSON_VALUE(<field>, '$.<op>')` interpolates `op` raw inside a
   single-quoted string literal. A key such as `x') = "" OR TRUE OR ('` closes
   the literal and injects SQL.

Both are reachable from `filter`/`where_cond` dictionaries; `AbstractParser._where_element`
(`abstract.pyx:565`) validates dict *values* with `is_valid`, never the keys.

### Goals
- G1. The Rust BigQuery builder never renders a top-level key that is not a safe
  SQL identifier (same rule as the Cython FEAT-103 check and `pg_safe_identifier_key`).
- G2. The Rust BigQuery builder never renders a JSON member key that is not a
  dotted identifier path (`[A-Za-z_][A-Za-z0-9_]*`, dot-separated).
- G3. Safe inputs render byte-for-byte as today (all existing `bigquery_parser::tests`
  and `tests/test_bigquery_partial_matching.py` stay green).
- G4. Both checks are covered by Rust unit tests and a Python-level test against
  the compiled extension (skip-guarded when the extension is stale).

### Non-Goals (explicitly out of scope)
- The Cython twin's dict-member key (`bigquery.pyx:246-250`) has the same JSON-path
  hole; it is filed as a sibling ledger issue, not fixed here (issue scope is the Rust path).
- Changing the error semantics of `bq_filter_conditions` (it keeps returning
  `PyResult<String>`; unsafe keys drop the condition — see §7 D1).
- PostgreSQL / SQL Server / generic SQL Rust builders.

## 2. Architectural Design

### Overview
Add two allow-list validators to `rust/src/bigquery_parser.rs` and call them at
the two render sites. Rejected keys return `None` from the per-entry builder, so
the condition is omitted exactly as the Cython path (`continue`) and the
PostgreSQL Rust path (`pg_safe_identifier_key(key)?`) already do.

### Component Diagram
```
bq_filter_conditions (Phase 1, GIL)          Phase 2 (rayon)
  └─ FilterEntry{key, value}  ──►  process_entry
                                     ├─ bq_safe_identifier_key(key)?   ← NEW (G1)
                                     ├─ resolve_json_field(...)
                                     └─ process_dict_value
                                          ├─ lookup(op)  (FEAT-180 LIKE forms)
                                          ├─ COMPARISON_TOKENS
                                          └─ bq_safe_json_member(op)?  ← NEW (G2)
                                               └─ JSON_VALUE(f, '$.<op>') = "<v>"
```

## 7. Implementation Notes & Constraints

### Decisions
- **D1 — drop, don't raise.** An unsafe key makes the per-entry builder return
  `None` (condition omitted). Raising from `bq_filter_conditions` was rejected:
  `BigQueryParser.filter_conditions` (`bigquery.pyx:130-137`) catches every Rust
  exception and falls back to `_filter_conditions_cy`, whose dict-member branch
  still interpolates the key — a raise would route the hostile key straight to
  the unprotected path. Dropping is also what FEAT-103 (`continue`) and
  `pg_safe_identifier_key(key)?` do, so the three builders agree.
- **D2 — one rule, two sites.** The top-level rule is the FEAT-103 rule verbatim
  (strip `|!~#@:`, numeric → quoted, alnum/`_`/`.` pass). The JSON-member rule is
  stricter (ASCII identifier path, no leading/trailing dot) because it lands
  inside a string literal and BigQuery JSONPath only needs identifier members.
- **D3 — empty-after-strip keys are rejected** (`!`, `||`): they cannot be a
  column; `pg_safe_identifier_key` lets them through, this twin does not.
- **D4 — Cython twin.** The same JSON-member hole in `bigquery.pyx:246-250` is
  filed as a sibling ledger issue (vulnerability, minor, about
  `querysource/parsers/bigquery.pyx`) rather than widened into this fix.

### Patterns to Follow
- Mirror `pg_safe_identifier_key` (`pgsql_parser.rs:25-35`) line for line, then add D3.
- Test names start with `test_bqkey_` so the cargo filter `tests::test_bqkey_`
  selects only this feature's tests (the dev baseline has one unrelated failing
  test, `test_process_str_negation`, which must stay unselected).
- Run cargo tests with `--no-default-features` plus `PYO3_PYTHON`/`LD_LIBRARY_PATH`
  (encapsulated by `run_cargo_lib_tests`).

### Known Risks / Gotchas
- A rebuilt extension is required for the Python-level test to exercise the fix
  (`make build-rust && make stage-rust`); the test probes the output and skips
  with reason "stale _qs_parsers" otherwise, never fails spuriously.
- `is_alphanumeric()` accepts non-ASCII letters (same as the PG helper); this is
  deliberate parity, not an oversight.
